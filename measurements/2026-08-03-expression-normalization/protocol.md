# Цена нормализации выражений на живом проекте

Дата: 2026-08-03. Ветка `neo`.

## Вопрос

Нормализация выражений для сравнения даёт каждой сущности второе поле, которое
заполняется на разборе проходом по потоку токенов. Сколько это стоит на настоящем
проекте и не изменился ли результат сравнения.

Сущности: предикат частичного индекса, выражения его колонок, `CHECK` на таблице,
предикат `EXCLUDE`, выражения расширенной статистики, `CHECK` на домене, условие
`WHEN` триггера.

## Что сравнивалось

| | ядро | описание |
|---|---|---|
| до | `1ff5da44` | последнее ядро без нормализации |
| после | `e6da0b0f` | ядро со всеми семью нормализованными сущностями |

CLI в обоих случаях `ec93403` — он не менялся; пересобирался против каждого ядра.
Сборка «до» разворачивалась во временном рабочем дереве, после замера убрана,
локальный репозиторий Maven возвращён к текущему ядру.

## Как мерили

Диф проекта OmniX_DB **против самого себя**:

```
java -Xmx4g -jar pgcodekeeper-cli-15.1.0-neo1.jar -s <OmniX_DB> -t <OmniX_DB>
```

Обе стороны читаются с диска, база не нужна, ничего не пишется. Проект — 22 386
файлов. Три прогона на каждой сборке, время замерялось целиком по процессу.

Такая форма даёт заодно санитарную проверку: проект, сравниваемый сам с собой,
обязан давать **пустой** скрипт.

## Результат корректности

**Скрипт пуст во всех шести прогонах, на обеих сборках.** Ни одного символа вывода.
Нормализация не внесла ложных различий на настоящем корпусе из 22 386 файлов.

## Результат по времени

| | прогоны, мс | медиана | среднее | разброс |
|---|---|---|---|---|
| без нормализации | 80 127 · 76 636 · 75 023 | 76 636 | 77 262 | 5 104 |
| с нормализацией | 78 170 · 76 067 · 84 016 | 78 170 | 79 417 | 7 949 |

Разница медиан: **+1 534 мс (+2,0 %)**. Разница средних: **+2 155 мс (+2,8 %)**.

## Вывод, и его честная граница

**Разница между сборками меньше разброса внутри каждой группы** — 1,5–2,2 секунды
против 5,1 и 7,9 секунды соответственно. На трёх прогонах это означает, что цена
нормализации **не отличима от шума измерения**, а не что она равна двум процентам.

Правильная формулировка: цена не превышает примерно **3 %** от полной загрузки
проекта. Более точное число потребовало бы десятка прогонов на незанятой машине с
фиксацией пауз сборщика мусора — здесь этого не делалось, потому что для решения
«достаточно ли дёшево» хватает верхней границы.

Что подтверждено твёрдо: скрипт не изменился, и просадка не измеряется десятками
процентов.

## Чего этот замер не покрывает

- Память и паузы сборщика мусора не фиксировались. Нормализованные строки живут в
  модели всю загрузку, то есть растёт постоянная куча, а не мусор молодого
  поколения. Для семи сущностей прирост мал, но не измерен.
- Сторона живой базы не участвовала: обе стороны читались из файлов. Пути чтения из
  каталога покрыты юнит-тестами каждой сущности, но не этим замером.
- Машина под нагрузкой не контролировалась; разброс до 8 секунд на одинаковых
  прогонах — прямое тому свидетельство.
